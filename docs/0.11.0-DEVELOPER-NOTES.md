# 0.11.0 — developer notes

Written 2026-10-06 on the Windows laptop. Three things since 0.10.0 (which
never shipped): the window (tui/gui.rs, 2026-09-25), the room (room.rs,
net.html, 2026-09-25), and the net front door with the briefing (2026-10-06).
The first two have their own commit messages (`cd968fc`, `ecc32ca`); these
notes cover the third in full and the other two in what they changed for it.

---

## 1. The window (tui/gui.rs)

`egui` 0.32 on the glow backend, `eframe`. This broke the project's "no
crates" rule, on the owner's order of 2026-09-25 ("a GUI in Rust for
everything"): a native window cannot be written in std. The phones' page is
still plain HTML/CSS/JS served by the std-only server.

The window is a child module of `tui`, so it drives `App`'s own handlers
(`home_key`, `pick_key`, `send_key`, `tick_key`...) with the keys the
terminal would have sent, and reads `App`'s state to draw. Nothing in `App`
knows whether a window or a terminal is drawing it. Where a screen needed
more than a key (the Open a net form), `App` got a method (`open_net_form`,
`open_the_net`) and the terminal shows its nearest screen instead.

Windows subsystem = windows (no console behind the window); every helper
program goes through `net::command()` with `CREATE_NO_WINDOW`, without which
`sc.exe` died with `0xc0000142`. Typed commands `AttachConsole`.
`HUB_GUI_TOUR=<dir>` walks every screen and saves a picture of each;
`HUB_GUI_DEBUG=<file>` logs input. Clicks driven from outside do not reach the
window on the test laptop (another window sits on top invisibly): use the
tour.

## 2. The room (room.rs, serve.rs `/net/*`, net.html, tui/member.rs)

One `Room` under a mutex: `lines` (#main, 500 kept), `people`, `check`,
`quiet`, `muted`, `topic` (the briefing, see 3), `op_nick`. One pulse counter
with a condvar; `/net/wait?since=&line=` is answered the moment anything
changes, or after `WAIT_FOR` (25 s), on a thread of its own, never on a
server worker (serve.rs explains the countdown a held worker starts).
`state()` renders one JSON object per answer: the viewer, the room, the
people, the viewer's private threads (all of them for the operator).

The operator is the laptop's own browser and only that (`serve::is_operator`:
127.0.0.1), or the window itself, which calls `room::*` directly. The window
and the page are two views of the same room; the benches drive the page.

`tui/member.rs` is a laptop joining another hub's room over the same doors a
phone uses (`/name`, `/net/*`), so the person in charge sees it as any other
member and every rule applies to it.

## 3. Open a net, and the briefing (2026-10-06)

**Why.** See the commit (`5b55d5f`). The old front door, "Hand out files to
the class", called `open_picker()` before anything else and `begin_sending`
refused without a folder; the wifi and the room were unreachable without one.

**The form.** `Screen::Open` (tui.rs). `App` fields: `net` (this lesson was
opened as a net), `net_folder` (a folder was chosen on the form),
`briefing`, `op_name`. `open_net_form()` sets them and goes to the form, or
to `FixOffer` first when parts of Windows are off. `form_screen()` is the
form a side trip returns to (`Open` or `Send`): the picker's Enter and Esc,
`finish_picking`, the tick screen's Back and `fixoffer_key` all go through
it, so the old flow is unchanged and the new one comes back to its own form.

**Starting.** `open_the_net()`: with no folder, `net_files_folder()` (an
empty *Gorilla Hub files for the team* next to `receive_dir`) is made and
becomes `folder`; then `open_tick(true)`. With a chosen folder and files, the
tick screen is shown for review, as handing out does, and its START goes on
to `begin_sending` + `after_net_start`. With nothing to review,
`apply_ticks`, `begin_sending`, `after_net_start` at once.
`after_net_start()` runs only if the screen reached `Sending` (a failed
start left a note instead): `room::set_op_nick(op_name)` and
`room::set_topic(briefing)`. This happens after `serve::start` so
`forget_session`'s `room::clear` (which runs at Stop) cannot wipe it.

**The briefing is the topic.** `Room.topic` keeps its name on the wire
(`/net/topic`, `"topic"` in the JSON, `/topic` in the typing line) so pages
and benches written before it was called a briefing keep working. New:
`topic_at` ("HH:MM"), `Person.read` ("HH:MM" or empty), `set_topic` clears
every `read` and says *set the briefing* in the room; `read_brief(key)`
stamps once per person per briefing and says *N read the briefing*;
`/net/readbrief` (members only) calls it and notes `sign-ins.txt`. The JSON
gains `topicat`, `me.read` (true for the operator) and `people[].read`.
`Snapshot`/`PersonView` carry the same for the window. `TEXT_CAP` (500)
applies to the briefing, up from 200 for the topic.

**On the pages.** net.html: `#brief` between the top bar and the log, shown
on # main; *I HAVE READ IT* when `!OP && topic && !read`; the operator's tool
is *Set briefing* (still `/topic `). A briefing that changes under a page
beeps. `drawNicks`: *not read yet* outranks an answered check (a check never
ends; who has not read new orders matters more), then *✔ time* / *waiting*
/ *read it*; the count line says *n / m read the briefing* when no check is
running. gui.rs: the same card above # main for the operator, with a
multiline editor behind *Change briefing*; the member's window shows the
briefing as a whole screen the first time (`member_entered`), with one
button, and as a card with the button afterwards; both people lists follow
the same order.

**Words.** The start screen, the menus (*Net* instead of *Lesson*), the
lesson's tabs (*Main channel*, *Who is on*, *Sent to you*, *Files for the
team*), the stop button and its questions say *net* when `app.net`, and keep
the class words otherwise. The in-window guide starts with *OPENING A NET*.

## 3a. A file into the channel (2026-10-12)

The owner, on the installed build, as a member on a phone: no way to send a
daily operations report or a sitrep to the net; `# files` only offered the
old `/classic#handin`, which is a private hand-in nobody in the channel
hears about.

- `room::LineKind::File`, `Line.file` (the name in the waiting area; empty on
  every other kind), `room::may_send` (the `say` gate, mute and quiet, asked
  BEFORE the body is read so a muted station cannot fill the disk) and
  `room::sent_file`. The JSON line gains `"file"`.
- `POST /net/file?to=<buffer>&token=`: multipart, streamed by the existing
  `page::take_upload` into the waiting area (so `serve::pending`, the Sent
  to you tab, accept and refuse all work unchanged); `UploadOutcome.landed`
  now carries (name, name on disk, bytes). On a net (`room::team()`) and
  `to=#main`: a File line in the room and `messages.txt` gets
  `#main  <who>: sent a file: <name> (<size>)  -> waiting/<on disk>`. In a
  class, or `to=@<own key>`: the same words go down the private chat
  (`page::take_talk`, kind text, token `file-<on disk>`), and the record
  says `<who>  -> waiting/<on disk>`. The operator may send too (to a
  private chat, or to # main on a net).
- `GET /net/f/<name on disk>`: the file back, as a download, from waiting/
  or, once accepted, from the received folder; never from refused/. Served
  only on a net or to the operator: in a class nothing a child sent is handed
  back out (unchanged rule). No path separators, no dot files, `..` refused.
- `net.html`: paperclip button `#attbtn` + hidden `#pick` (multiple); XHR
  `FormData` upload with `upload.onprogress` into the note above the typing
  line; result words `ok | muted | quiet | toobig | cantsave | empty | no |
  lost`; File lines draw a `GET IT` link (`download` attribute). Eight new
  words in the six languages (AI drafts, like the rest).
- `hub serve --net` sets `room::set_team(true)` so a bench can run the net
  path without the window.
- Window: `BLUE_FILE` for File lines in `line_row`; `member.rs` maps
  `"file"` to `LineKind::File`. The member window shows the line but has no
  GET IT yet: a laptop member opens the page in a browser for that.

## 4. Bench

`bench/net-briefing-test.py` 1.0.0: one phone through a relay and the
operator's page; sets the briefing through `/net/topic` (the same door the
page's button uses), checks the card and button on the phone, *not read yet*
and the count on the operator's page, the tap, *read it*, the line in the
room, a changed briefing unread again, and `sign-ins.txt`. 20 checks. Run
it on a fresh hub: a room left by an earlier bench keeps its people online
for 45 s and its comms check for ever, and the counts then include them.

`bench/net-chat-test.py` 1.1.0 adds the paperclip: a phone sends a text
file; in a class (default) it must NOT reach the other phones and the phone
says *Sent to your teacher*; with `--net` (hub started with `--net`) every
phone and the operator see the line, a second phone presses GET IT and the
bytes match; either way the file is in `received/waiting` and
`messages.txt` names it.
