# The test that failed once in twenty-five runs, and why that mattered — Plain Language

## What happened

While tidying up the notes in the source code, the tests were run several times
rather than once. One of them failed. Running it again, it passed. Running the
whole set another ten times, it passed every time.

That is the moment where most people move on, and it is the wrong moment to
move on. A test that fails occasionally is not noise. It is a test trying to
tell you something in the only way it can.

It was run sixty more times until it failed again, this time with instructions
to write down exactly what it saw.

## What it was actually saying

The test checks something important: **a child's homework must not reach the
teacher's folder until the teacher has accepted it.** It sends two files, then
checks the teacher's folder is still empty.

Sometimes the folder was not empty. There was a file in it.

The file was real. It was homework, it had been accepted, and it had been put
there by the very same test — during a completely different run, about half an
hour earlier.

## Why that could happen

Every test needs a scratch folder to work in. Each one named its folder after
its own process number, on the reasonable assumption that a process number
identifies a program while it is running.

It does, and only while it is running. Windows hands the same number out again
to the next program once the first has finished. Nothing here ever deleted its
folder, so a run that happened to draw a recycled number opened a folder that
already had somebody else's finished work sitting in it.

Counted on this machine: **1,458 abandoned folders, across 112 different
process numbers, from about 150 runs.** Reuse was not a rare accident. It was
happening constantly, and only sometimes landing on a folder whose contents
changed the answer.

## Why this is worth a document

This release exists because of a bug of exactly this shape. The program checked
whether it was safe to hand out addresses, got an answer, and then repeated
that answer for the rest of the day without ever looking again. It described a
world that had been true earlier and presented it as now.

The tests that certify the program cannot do that were doing the same thing.

That is not an amusing coincidence. It is the reason to take it seriously: a
measuring instrument with the same fault as the thing it measures cannot be
trusted to find that fault.

## What changed for you

Nothing, if you use the program. Not one line that runs on your machine was
touched. This is entirely in the test harness.

What changed for anybody working on it:

- Scratch folders are named with the time they were made as well as the process
  number, so a recycled number cannot collide with anything.
- A folder is emptied before it is used, so even an impossible collision starts
  from nothing.
- Folders left by earlier runs are cleared out automatically after an hour —
  long enough that a run happening at the same time is never disturbed.
- Two new tests check those properties directly, rather than hoping.

## How to check this yourself

```bash
cd src/hub && cargo test --release
```

100 tests, where there were 98. The two new ones are
`scratchdir::tests::two_scratches_are_never_the_same_folder` and
`scratchdir::tests::a_scratch_starts_empty_even_if_the_name_repeats`.

The cleanup was checked by making a folder, setting its date to three hours
ago, making a second one dated now, and running the tests: the old one was
removed and the new one was left alone.

## Honest state of play

The failure happened roughly once in twenty-five runs before the fix. Since the
fix, forty-five consecutive runs have passed.

Forty-five clean runs is **not** proof on its own. At the old failure rate you
would expect about two failures in that many runs, and seeing none has maybe a
one-in-six chance of happening by luck alone. The confidence comes from having
found the actual mechanism, reproduced it with the evidence written down, and
removed it — not from the run count.

## Should you be concerned?

No. Nothing that reaches your computer changed, and the thing that was wrong
made a test occasionally report a problem that was not there. It never hid a
real one.

## Glossary

**Process number (PID)** — a number the operating system gives a running
program so it can tell it apart from the others. Reused after the program ends.

**Scratch folder** — a throwaway folder a test works in so it does not disturb
anything real.

**Flaky test** — one that passes and fails on the same code. Almost always a
sign that something is being shared that should not be.
