# 0.9.7 — developer notes

A diagnostic for machines that have been modified, and why the message is the
feature rather than the check.

Written on the Windows laptop, 2026-09-08.

---

## The thing being diagnosed

Windows Settings → Network & internet → Mobile hotspot, on the machine this was
written on:

```
(x) We can't set up mobile hotspot.

    Mobile hotspot                         Off
    Share my internet connection from      [empty dropdown]
    Share over                             Wi-Fi
    Properties
        Name:
        Password:
        Band:
        Scan to connect:
```

The properties are **blank, not wrong**. That is the diagnostic signature: the
UI has nothing to read because the service that owns those settings is not
running.

### Measured cause

```
icssvc         Start=4   (Windows Mobile Hotspot Service)     default 3
SharedAccess   Start=4   (Internet Connection Sharing)        default 3
```

`4` is Disabled. `3` is Manual, which is what Windows ships.

### Everything that was ruled out first

Recorded because the wrong diagnosis here is cheap to reach and expensive to
act on.

| checked | result | meaning |
|---|---|---|
| `netsh wlan show wirelesscapabilities` | `Wi-Fi Direct GO: Supported`, `P2P Max Mobile AP Clients: 8` | the radio can do it |
| the same, `Soft AP: Not supported` | **red herring** | that is the Windows 7 `hostednetwork` path; Windows 11 uses Wi-Fi Direct GO |
| `HKLM\SOFTWARE\Policies\Microsoft\Windows\Network Connections` | only `NC_PersonalFirewallConfig`; no `NC_ShowSharedAccessUI` | no group policy is forcing this, so it can simply be set back |
| `icssvc` `DependOnService` | `RpcSs`, `wcmsvc` — both Running | dependencies are fine |
| `SharedAccess` `DependOnService` | `BFE` — Running | dependencies are fine |
| `WlanSvc` | Running, `Start=2` | wifi itself is untouched |

The machine had **150 services** set to Disabled. `icssvc` and `SharedAccess`
are collateral from a debloat pass, not a targeted change.

`WFDSConMgrSvc` (Wi-Fi Direct Services Connection Manager) is also disabled
here. It is **not** a declared dependency of either service, so it is listed
third and last, and the message asks for it separately. Changing one thing at a
time is how anybody finds out which change mattered.

---

## Why this belongs in the program at all

The strict reading is that this is not the hub's bug. The strict reading is
wrong for this project.

The tool exists for second-hand hardware in rooms with nobody to ask. A laptop
that has had a previous owner has usually been tuned by somebody, and Windows
answers that tuning with a red bar and an empty box. Nothing on that screen
names a service. A teacher's next move is to conclude the laptop is too old, or
that this program does not work, and both conclusions end the lesson.

`doctor` already exists to answer "what can this computer do, when there is
nobody nearby to ask". This is exactly that question.

## Implementation

`net.rs`:

```rust
const HOTSPOT_SERVICES: [(&str, &str); 3] = [ ... ];
fn start_value_from(text: &str) -> Option<u32>;          // cfg(not(linux))
pub fn disabled_hotspot_services() -> Vec<(&'static str, &'static str)>;
pub fn switched_off_advice(off: &[...]) -> Option<String>;
```

### `reg query`, not `sc qc`

The one decision worth defending.

```
> reg query "HKLM\SYSTEM\CurrentControlSet\Services\icssvc" /v Start
    Start    REG_DWORD    0x4
```

`REG_DWORD` is a type name. `Start` is a value name. `0x4` is a number. **None
of the three is translated** on a Windows installed in another language.

`sc qc icssvc` prints `START_TYPE : 4 DISABLED`, and both `START_TYPE` and
`DISABLED` *are* translated. Anything matching on those words would work in
London and quietly fail in Kabul — which is not a hypothetical for this
project, and is the identical trap that made `net::connected_addresses()` test
for membership in a tool's output rather than parse the label `IPv4 Address`
out of it. Second time; hence written down again.

The parser is a separate pure function so the localisation argument is testable
rather than asserted in a comment.

### Failure is silence, not alarm

A `reg` that will not run, a key that is missing, a non-zero exit, a value that
is not a hex DWORD — all produce "this service is fine". Being unable to answer
the question is not evidence of a fault, and a diagnostic that invents problems
is worse than one that stays quiet. The cost of a false positive here is a
teacher typing `Set-Service` commands at a machine that was already correct.

### Cost

Three `reg query` invocations, only on `doctor` and only on the hotspot error
path. Nothing on any path that serves a file, and nothing on Linux, where the
function is a `Vec::new()` stub.

## The message, which is the actual work

Four decisions, each of which is a failure mode avoided.

**The exact words to type, not "enable the services".** The gap between those
two is the entire problem: anybody who knew how to enable a Windows service
would never have needed the message. This is the same principle as
`explain_nmcli`, which exists because nmcli's errors are written for
administrators.

**Each service named twice**, in plain words and by service name. The plain
name is what appears in `services.msc`; the service name is what can be typed,
searched, or read down a phone line.

**"It is not the wifi card", first line.** That is the wrong conclusion people
reach, and the one that makes them stop.

**A way out for somebody who is not allowed.** A managed or locked-down laptop
is a legitimate configuration, and this must not read as "fight your IT
department". The commands need Administrator, so nobody can act on this without
already having the right to; and the cable path needs none of it. Said out
loud, because the alternative is a person who cannot follow the instructions
and is told nothing else.

**Placed at the bottom of `doctor`, not beside the wifi line.** Tried it beside
the wifi line first — it is contextually the right place and it is wrong. Every
other line of `doctor` is one fact, meant to be scanned or read aloud. Ten
lines of prose in the middle breaks that for exactly the machines that have the
problem, i.e. the ones whose owner most needs the lines underneath. The list
stays a list.

## Tests

Five new, `net::switched_off_tests`. **Four of the five are about the message
rather than the mechanism**, which is deliberate: on a screen like this the
message is the feature, and a check that detects correctly and explains badly
has failed.

- `the_start_value_is_read_as_a_number_and_not_as_a_word` — real captured
  output, plus `0x3`/`0x2`, plus a localised sample, plus four inputs that must
  yield `None`. This is where a future refactor that starts matching on a word
  should fail.
- `a_machine_with_nothing_switched_off_is_told_nothing`
- `the_advice_names_the_service_and_the_exact_words_to_type` — asserts each of
  the four decisions above, individually, because the message is worthless
  missing any one of them
- `the_advice_does_not_name_services_that_are_fine` — a message listing three
  services when one is off sends somebody to change two things that were
  already right, and destroys the evidence of which change mattered
- `asking_this_machine_returns_only_names_we_know` — runs against whatever this
  machine actually is. It cannot assert a result, because both answers are
  correct on different hardware; it asserts the failure that would put an
  invented service name in front of a teacher

115 tests total.

## ⚠ Claimed but not verified

- **`WFDSConMgrSvc` is a judgement call, not evidence.** It is not a declared
  dependency, and see the measurement below: during a hotspot that started
  successfully, it never left `Stopped`. That is evidence it is not needed, but
  not proof, because the run that worked had it set to `Manual` along with the
  other two and no run has yet been made with it left `Disabled`. It stays last
  and separate in the advice until somebody isolates it.
- **The localisation claim is reasoned, not measured.** `REG_DWORD` not being
  translated is documented behaviour and consistent with every `reg` output
  seen, but no non-English Windows was available to test on. The test carries a
  sample rather than a machine.
- **The four cable behaviours** from the 26-09-08 handover are still unrun on
  Windows: the `gorilla.local` collision refusal, the promise when there is no
  collision, the receive list naming the other machine over `/?who`, and the QR
  on a cable. They need the second laptop.

## The fix, measured

Performed on this machine 2026-09-08, elevated, with the restore in a `finally`
and the before-state captured rather than assumed — the same shape as
`bench/cable/`, and for the same reason.

The test does not read the Settings window. It asks the API that window is a
front end for:

```
[Windows.Networking.NetworkOperators.NetworkOperatorTetheringManager]::CreateFromConnectionProfile($profile)
```

**Before**, with all three `Start=4`:

```
internet profile: ASK4 Wireless
CreateFromConnectionProfile -> Exception from HRESULT: 0x83120001
```

That failure IS the red bar. Settings cannot build a tethering manager, so it
has nothing to populate the boxes from, and it reports the only thing it knows:
"We can't set up mobile hotspot."

**After** `Set-Service ... -StartupType Manual` on all three and
`Start-Service icssvc`:

```
icssvc          Running   Manual
SharedAccess    Stopped   Manual
WFDSConMgrSvc   Stopped   Manual

manager created:   YES
operational state: Off
max clients:       8
ssid:              'WIN-VR6KGAH3RAF 5437'
passphrase length: 8
band:              Auto
```

The empty boxes were empty because nothing could answer. Given a service to
ask, Windows produced a name, a password and a band immediately.

Then it was actually started, not merely made configurable:

```
operational state now: On
clients connected: 0
adapters up: Wi-Fi, Ethernet, Local Area Connection* 2
```

`Local Area Connection* 2` is the virtual access point. The wifi station
connection stayed up throughout, which is what a Wi-Fi Direct GO is supposed to
do and is worth knowing before recommending this to somebody working over that
same wifi.

**After restoring**, all three back to `Start=4` and `Stopped`:

```
CreateFromConnectionProfile -> Exception from HRESULT: 0x83120001
```

A/B/A. The failure returns when the change is undone, which is what makes this
a measurement of the cause rather than a coincidence.

### Two things that fell out of it

**SharedAccess never ran.** It was set to `Manual` and stayed `Stopped` for the
whole successful run, hotspot included. What matters is that it is *startable*,
not started — something starts it on demand later, or not at all. The advice
does not tell anybody to start it, which turns out to be correct by accident
rather than by design.

**`WFDSConMgrSvc` never ran either.** Same reasoning, and it weakens the case
for including it at all. It has been demoted in the notes above from "judgement
call" to "judgement call with evidence against it". Settling it properly needs
one more run with that service left `Disabled` while the other two are `Manual`.

### The restore did not work first time

Worth recording, because it is the failure this kind of script exists to
prevent and it happened anyway.

`StartTetheringAsync()` returns an `IAsyncOperation`, and the poll compared
`$op.Status` against the integer `1`. It never matched, so the script decided
the start had failed, so the `finally` skipped `StopTetheringAsync()`, so the
hotspot was left running and `Stop-Service icssvc` could not stop a service
that was mid-tether. It printed **`*** NOT FULLY RESTORED ***`**, which is the
one thing it got exactly right.

Final state after a second elevated pass: all three `Start=4`, all `Stopped`,
tethering `Off`, wifi still connected. Verified independently afterwards rather
than trusted from the script's own summary.

The lesson is not about PowerShell. It is that the check which decides whether
to clean up must not be the same check that decides whether the thing worked:
the cleanup should have run on "we called start at all", not on "start
reported success".

The script is kept as `bench/hotspot-services-test.ps1`, with that fixed and
the reason written next to it, so the next person to need this measurement does
not write it again under time pressure.

## Housekeeping found, not fixed here

**~20 junk Windows Firewall rules from `cargo test`.** Every test binary that
opens a socket triggers a firewall prompt and leaves a permanent rule behind:

```
hub-f22675d02e5febf9.exe   ...\target\release\deps\hub-f22675d02e5febf9.exe
hub-32675b08e23229c1.exe   ...
```

14 of them at last count, TCP and UDP, one pair per test-binary hash, and they
breed every time the hash changes. Deleting them needs Administrator, so it
could not be done from the session that found them. They are inert, but they
accumulate forever and clutter the rule list a person has to read when
`reachable` says NO.

To clear them, in an Administrator PowerShell:

```powershell
Get-NetFirewallRule |
  Where-Object { $_.DisplayName -match '^hub-[0-9a-f]{16}\.exe$' } |
  Remove-NetFirewallRule
```

That pattern matches only test-binary hashes. It leaves `hub.exe` and
`Gorilla Hub` — the rule `hub fix-firewall` creates — alone.
