# hub 0.9.1: a stale-state fault in the test harness, found by not accepting a rerun

## Problem Being Solved

`page::tests::work_waits_until_accepted_and_a_refusal_is_kept` failed
intermittently, roughly one run in twenty-five, and passed on every rerun in
isolation. The assertion that failed is the one that matters most in that test:
that nothing reaches the teacher's folder before she accepts it.

## Approach Taken

Not rerunning until green. The suite was run in a loop with the failure
captured, then the assertion was temporarily replaced with a diagnostic that
dumped the directory listing, the resolved device label and the process-wide
`PENDING` queue, and the loop was run again until it fired.

## Before

Five test modules each built a scratch directory named
`hub-<module>-test-<pid>[-<tag>]` under the system temp directory. None removed
it afterwards. `tui.rs` keyed on pid alone; the rest on pid plus a tag or a
counter.

## After

`scratchdir::scratch(tag)`, `#[cfg(test)]` only, used by all five. The name
carries pid, nanoseconds since the epoch and a counter; the directory is
removed before creation; directories older than one hour matching either the
new prefix or any of the five legacy prefixes are swept once per process.

## The evidence

The diagnostic, from run 26 of 60:

```
DIAG dir="…\hub-page-test-19724-11" label="10.42.0.98"
  [handed-in]          "10.42.0.98--good.txt"     <- stale
  [handed-in/waiting]  "10.42.0.98--bad.jpg"      <- fresh
                       "10.42.0.98--good.txt"     <- fresh
  [handed-in/refused]  "10.42.0.98--bad.jpg"      <- stale
```

Both the accepted and the refused file were present *before* this run's accept
and refuse had executed, alongside this run's freshly uploaded copies. That is
the terminal state of a completed earlier run, inherited whole.

`a_hostile_filename_cannot_leave_the_folder` failed in the same run, from the
same cause.

Measured on the machine: **1,458 leftover directories across 112 distinct pids
in approximately 150 runs.** Windows recycles pids quickly enough that
collision was routine; it only produced a failure when the recycled directory
belonged to a test whose leftover state contradicted a later assertion.

## Decisions Made

- **Timestamp in the name rather than a random number.** No crates, and
  `SystemTime` is already a dependency of the timestamping code. Nanoseconds
  plus pid plus counter is unique enough for a test harness and, unlike a
  random number, sorts usefully when reading a listing by hand.
- **Sweep on read, not teardown.** A `Drop` guard per test would be the
  textbook answer and would need touching every test that makes a directory,
  including ones that deliberately leave state for an assertion. Sweeping by
  age at startup costs one `read_dir` per process and also cleans up after
  every run that predates this change.
- **One hour, not one minute.** The only hazard is deleting a concurrently
  running suite's directories. A run takes under two seconds; an hour is three
  orders of magnitude of headroom for zero practical cost.
- **The legacy prefixes are swept too.** Otherwise the 1,458 directories
  already on this machine, and whatever is on anybody else's, stay forever.
- **`remove_dir_all` before `create_dir_all`.** Redundant given the timestamp,
  and kept: the property being guaranteed is "this directory starts empty", and
  guaranteeing it directly is cheaper than reasoning about whether the name can
  collide.

## Tried and Abandoned

- **Rerunning and moving on.** The first two failures were dismissed as
  environmental. Recording this because it was very nearly the end of the
  investigation and would have left a real fault in place.
- **Blaming parallelism against `PENDING`.** `serve::PENDING` is process-wide
  and the test's own doc comment warns about exactly that class of problem, so
  it was the first hypothesis. It is innocent: `accept_pending` resolves paths
  from the `root` it is passed, and the queue never touches disk.

## ⚠ Claimed But Not Verified

- **That the flake is gone.** 45 consecutive clean runs, against a prior rate of
  about 1 in 25. At that rate the expected number of failures in 45 runs is
  ~1.8, so observing zero has a probability of roughly 0.16 under the null —
  suggestive, not decisive. The confidence rests on the mechanism having been
  identified, reproduced with evidence, and removed, not on the run count.
- Whether the same pid-reuse pattern exists in the PowerShell harness under
  `bench/cable/`. Not audited.

## How to verify this work

**Step 1:**
```bash
cd src/hub && cargo test --release
```
  - **Pass:** 100 passed, including the two new `scratchdir::tests`.
  - **Fail:** `two_scratches_are_never_the_same_folder` failing means a tag has
    been allowed back into the identity of a directory.

**Step 2:**
```bash
mkdir "$TMPDIR/hub-test-x-999-old" && touch -d '3 hours ago' "$TMPDIR/hub-test-x-999-old"
mkdir "$TMPDIR/hub-test-x-999-new"
cargo test --release two_scratches
```
  - **Pass:** the old directory is gone, the new one remains.
  - **Fail:** both gone means the age threshold is not being applied and a
    concurrent run could have its directories deleted underneath it.

**Step 3:**
```bash
for i in $(seq 1 45); do cargo test --release >/dev/null 2>&1 || echo "run $i failed"; done
```
  - **Pass:** no output.
  - **Fail:** any output. Capture it before rerunning — the evidence does not
    survive the next run, which is the whole lesson here.

## Packaging, and what the artifacts are worth

`packaging/build-linux-tarball.py` is new. The Linux archive had no script: it
was assembled by hand from `dist/`, which is in `.gitignore`, and its
`README.txt` existed nowhere else in the project. A `rm -rf dist` would have
lost it silently, and the next release would have shipped a binary with no
instructions. The readme is now `packaging/linux-README.txt`, and the version
drift test covers it along with `build-linux-tarball.py`,
`build-windows-zip.py` and `windows-README.txt` — four files it did not guard
before.

The script refuses to build unless the binary is ELF, 64-bit, little-endian,
x86-64, contains the string `hub <version>` in its own bytes, and carries no
Windows resource section. The version check exists because this project has
already come within one command of publishing a stale Linux binary under a
fresh checksum, which is the failure that defeats every verification a user
can run.

**Reproducibility, measured rather than claimed:**

- The Linux tarball is byte-identical across independent builds. Two runs
  produced sha256 `004ff914…b00e` both times.
- The Windows binary is **not**. Two builds of identical source differ in
  exactly three bytes, at 0x88 and 0xd8: the PE `TimeDateStamp`
  (`0x6a9ece7a` -> `0x6a9ecea4`) and the header checksum derived from it. Every
  other byte of 828,928 is identical.

So "rebuild it and compare the checksum" works as an audit for Linux and needs
those two fields masked for Windows. The zip's fixed member timestamps make
the container reproducible; the binary inside it is what varies.

## Technical Debt

🟡 **LOW** — The sweep does one `read_dir` of the system temp directory per test process → On a machine with a very large temp directory this is measurable. It is one call and it is behind a `OnceLock`.
🟡 **LOW** — `net.rs` test module has an unused `use super::*` → Pre-existing; not touched here to keep this diff to one subject.
🟡 **LOW** — The Windows binary is not byte-reproducible → Three bytes, all PE metadata. Fixable by stamping a fixed `TimeDateStamp`, which means post-processing the PE header or passing a linker flag; not worth doing blind, and worth doing before anybody is asked to reproduce a Windows release.
🟡 **LOW** — `packaging/build-linux-static.sh` had CRLF line endings → Harmless under Git Bash, fatal on Linux, where `` becomes part of the command. Worth a `.gitattributes` entry forcing LF on `*.sh`.
