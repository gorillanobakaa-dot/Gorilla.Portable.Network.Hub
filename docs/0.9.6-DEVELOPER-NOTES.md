# 0.9.6 — developer notes

The audit trail for a one-line release, plus the three Windows-side commits
that shipped inside 0.9.5's Windows zip and were never written up anywhere but
a commit message.

Written on the Windows laptop, 2026-09-08.

---

## The fault

`main.rs::doctor()` had:

```rust
match net::wifi_interface() {
    Some(i) => println!("  wifi adapter   {i}"),
    None => println!("  wifi adapter   none found, so this computer cannot make a network"),
}
```

and `net.rs` has:

```rust
#[cfg(not(target_os = "linux"))]
pub fn wifi_interface() -> Option<String> {
    None
}
```

So on every system that is not Linux, the `None` arm is not a search result. It
is unreachable-by-any-other-path, and the sentence is printed unconditionally.

### The evidence, measured while it was printing

```
  wifi adapter   none found, so this computer cannot make a network
```

At the same moment, on the same machine:

```
netsh wlan show interfaces  ->  Wi-Fi, State: connected, SSID: ASK4 Wireless
Get-NetAdapter              ->  Intel(R) Wi-Fi 6 AX201 160MHz, Up, 173.3 Mbps
```

### Why the conclusion was still right

`hotspot_up()` is `nmcli` and is `#[cfg(not(target_os = "linux"))]` compiled to
an `Err` carrying the advice:

> On this system, switch the hotspot on yourself: Settings, Network and
> internet, Mobile hotspot. Then come back here and the files will be handed
> out over it.

So the program genuinely cannot create the network itself here. `doctor` and
`hotspot_up` were giving a person two different accounts of the same laptop,
and the one that ran first was the discouraging one.

This is the same class as fixes (b) and (f) on the Debian side: a message that
compiles and runs and is wrong only on the system nobody was looking at.

### The fix

`wifi_lines() -> Vec<String>`, split out of `doctor()` so it can be tested at
all, with the Linux behaviour byte-identical and the other branch replaced.

**Deliberately no detection on Windows.** `netsh wlan show interfaces` would
name the adapter, and its field labels are translated on a Windows installed in
any other language. That is precisely the trap that made
`net::connected_addresses()` test for *membership* in a tool's output rather
than parse a label out of it, and the reasoning is recorded there. Here there
is nothing to gain: the advice is identical whether an adapter is present or
not, so a fragile parse would buy one cosmetic word at the cost of a new bug on
every non-English install.

Also deliberately: the new text does not say "not checked". It says what the
program can and cannot do and where the switch is. A `doctor` line is read by
somebody who is stuck, and "not checked" gives them nothing to do.

### The guard

`doctor_tests::doctor_does_not_claim_a_missing_wifi_adapter_on_a_system_it_never_looked_at`

Asserts, off Linux, that the output does **not** contain `none found` and
**does** contain `Mobile hotspot` — the second half because the failure mode
worth preventing is not just the false claim, it is `doctor` disagreeing with
`hotspot_up` about where the switch is.

On Linux the test returns early rather than asserting the old string, so it
does not become a second place the Linux wording has to be kept in step.

## What shipped in the 0.9.5 Windows zip and is not written up elsewhere

These were made on this side while building 0.9.5 for Windows. They are in the
published zip; only the commit messages describe them.

### 1. The suite failed at random on Windows, about one run in five

Not a Linux-side finding. Present on `v0.9.4` and `v0.9.5` both.

```
before   2 failures in 11 full runs   (~18%)
after    0 failures in 25 full runs
```

Always `serve::block_tests::a_paused_device_gets_nothing_and_a_freed_one_gets_it_back`.
Always at the `POST /note`, never at the three `GET`s before it. Never once
under `--test-threads=1`.

**Cause: two serial locks that did not exclude each other.**
`block_tests::ONE_AT_A_TIME` and `walk_tests::TICKS` were separate `Mutex<()>`
statics, while both modules reach the same process-wide statics.
`walk_tests::a_finished_transfer_leaves_nothing_behind` calls
`forget_session()`, which clears `BLOCKED` among everything else — so it could
wipe the block that `block_tests` had just set and was in the middle of
proving.

The positional detail is the proof, not decoration: the wider the wall-clock
gap between `block_device()` and an assertion, the more chance the sibling
lands inside it. The `POST` is the last and furthest assertion in that test.

Both now take one module-level `SESSION_LOCK`. `walk_tests` takes it under the
old name via `use super::SESSION_LOCK as TICKS;`, so the call sites did not
have to change.

**Worth the Linux side's attention:** nothing about this is Windows-specific in
principle. Only the thread interleaving differs.

### 2. `VS_VERSIONINFO`, so Explorer knows what the file is

Closes the handover's section 5 item. `build.rs` already writes a resource
script and compiles it with `windres` for the icon, so the version block goes in
the same script. Still zero crates.

- `FILEVERSION` needs four numbers and the crate version has three, so the
  fourth is `0`, and all four are parsed from `CARGO_PKG_VERSION` rather than
  typed. A version maintained in two places is a version that will disagree
  with itself, which is the exact drift `every_packaging_recipe_names_this_version`
  exists to catch.
- `0809` (en-GB) and `04b0` (codepage 1200) must appear twice and agree, once as
  the `StringFileInfo` block name and once in `Translation`, or Explorer shows
  nothing and reports no error anywhere.

Verified rather than assumed, which is what the handover asked for about the
icon: Explorer reports `FileVersion 0.9.5`, `ProductVersion 0.9.5`,
`Gorilla Portable Network Hub`, `Gorilla`, and the AGPL line. The icon still
extracts as a 32×32 colour image, so the version resource did not displace it.

Cost: **1,024 bytes** (837,632 → 838,656).

One thing to note in `build.rs`: the icon path is now built with
`std::path::MAIN_SEPARATOR` rather than a `'\\'` literal. Same result, and it
avoids a backslash literal in a file that is otherwise full of them.

### 3. `check-both-builds.sh` runs on a Windows host

The Debian side asked for "the reverse check". A second script would drift from
the first, so this is the same script made host-aware.

Run on Windows as it stood, it would have built the Windows binary **twice**
(`cargo build --release` is the native build on either host) and then reported
that every windows-only string was present in the "linux" build. It would have
**passed, loudly, having checked nothing** — the one failure mode a check like
this must not have.

Now: host detected from `uname -s`; the *other* target is the cross-compiled
one; on Windows that cross build is delegated to
`packaging/build-linux-static.sh` rather than being a second recipe that can
drift from the one the release is cut with.

Two smaller faults found while doing it, both of which would bite on a Linux
host too:

- `strings(1)` is not on a Windows box. `grep -a` straight at the file needs no
  such tool and reads the same.
- **`grep -c` prints its count AND exits 1 when the count is zero.** So the
  original `$(... || echo 0)` appended a *second line*, every later `[ ]` test
  died on `integer expected`, and the script printed `FAIL` for text that was
  in exactly the right place. `|| true` keeps the count it already printed.

Output on this host:

```
host: windows
[ok]   windows build (native)
[ok]   linux build (cross, static musl)
[ok]   linux-only: install the .deb, which grants it once
[ok]   windows-only: IIS, Skype or Windows
[ok]   windows says: hub 0.9.5
[ok]   linux carries the string 'hub 0.9.5' (NOT run: this host cannot execute it)
both builds agree.
```

The Linux binary is compiled and inspected but **not executed**, because this
host cannot run it and there is no wine here. That is a real gap; the script
says so on the line rather than leaving it to be assumed.

## What was verified on real Windows

From the published zip, unpacked, not from `target/`:

- `hub doctor` lists the **cable address** `169.254.87.61` alongside the wifi
  one, and names the cable at `1000 Mbps`. That is the Debian side's fix (a),
  `set_broadcast(true)`, and it is the thing that had never once worked. It
  works here.
- `hub cable-get` found the sender with nothing typed, named it
  (`Found Teacher at 169.254.87.61`) rather than printing bare numbers — fix
  (d), `/?who` — showed a destination path with **no `\\?\` prefix** — fix (f)
  — and printed `1 piece` / `20 pieces` / `29 B` correctly — fix (g). 41.9 MB
  moved, all 7 files arrived.
- The port 80 branch was checked **by content, not by running**: the Windows
  binary contains `IIS, Skype or Windows` and does not contain
  `install the .deb`, both directions checked against the Linux binary in the
  same run. Deliberate: this laptop is on a shared residential network and
  starting a file server on it unasked is not a reasonable thing to do to find
  out what a message says.

## Tried and abandoned

**Detecting the wifi adapter on Windows with `netsh`.** Measured here:
`netsh wlan show interfaces` exits 0 and prints
`There is 1 interface on the system:` followed by an indented
`Name : Wi-Fi`. Rejected on two grounds. First, both of those strings are
translated on a non-English Windows, and I could not measure the
no-adapter case on this machine to know whether the exit code alone would carry
the answer — so the fallback would have been a parse I had no evidence for.
Second, and decisive: it would change one cosmetic word and nothing about the
advice.

**Publishing a Linux tarball for 0.9.6 from here.** It builds — the cross build
is part of `check-both-builds.sh` and passes. Rejected because the Debian side
cuts its tarball with `musl-gcc` and this one uses `zig`, and the two are not
the same bytes (992,592 vs 913,016 at earlier versions, for exactly this
reason). Two different files on two release pages both claiming to be the same
version is the drift this project keeps catching itself on, and it would be
self-inflicted.

## Housekeeping done on this machine, not in the repository

The installed copy at
`AppData\Local\Programs\PortableNetworkHub\hub.exe` was **0.9.0** — five
versions behind — and had been running since 11:48 the previous day.

Checked before stopping it, and worth recording:

```
udp 67   (the address server)
udp 53   (the resolver)
tcp 80, 8080
```

It had been holding a **DHCP server open for roughly 24 hours on a laptop that
had since joined a shared wifi network**, which is the single thing the guard
exists to prevent. It is the stale-state fault described in the 0.9.0 notes: the
guard was evaluated once, at start, when the machine was on a bare cable, and
never looked again. `dhcp::supervise` re-reads every three seconds now, and a
freshly started 0.9.5 on this machine correctly reports
`cable addresses  not offered here, which is correct on a network with a router`.

Whether it actually answered anybody cannot be established after the fact.
The socket was open; that is all that can honestly be said.

All four ports released on stop, and the wifi and every address survived it.
