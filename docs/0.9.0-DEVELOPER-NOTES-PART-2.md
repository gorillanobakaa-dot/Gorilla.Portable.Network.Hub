# hub 0.9.0: three stale-state faults in the DHCP guard, and the UI faults that only a user found

> Session record generated 2026-09-07

---

## Problem Being Solved

The cable data path was already proven: 45 MB across a bare CAT cable between a Windows and a Debian laptop, archive and individual files, nesting intact. Everything around it was not. Five faults were reported by the owner in ordinary use, and none had been caught by the test suite, because all five belong to a class a program cannot assert about itself: an action that succeeds while changing nothing on screen, and a decision that reports a state which was true earlier and is not true now.

The substantive one: dhcp::safe_to_offer refuses to serve on a machine that is also on a routed network, because a second DHCP server on a school LAN is a building-wide outage. The owner switched the wifi off, as the screen instructed, and the screen did not change. That turned out to be three independent stale readings layered on each other, and repairing the first two left it still broken.

## Approach Taken

Treat 'the screen said nothing' as a defect class and not a cosmetic complaint, and treat every network reading as suspect until its freshness is established.

For the guard, replace a decision made once at startup with a supervisor that re-evaluates on a three-second cycle and starts the servers when the way clears; replace 'which source address would the kernel pick' with 'which addresses are on interfaces the platform still considers connected'; and replace 'is there a gateway' with 'is there a router that has actually spoken to this machine', read from the neighbour table.

Each network reading is taken by MEMBERSHIP of an address in a platform tool's output, never by parsing a label, because the labels are localised and this ships to machines installed in other languages.

## Before

safe_to_offer(addresses, gateway) called once from begin_sending/cable_send; addresses from net::local_addresses() (UDP connect probes); gateway from net::default_gateway() (on Windows, '.1 of whatever subnet a probe lands on'). tui.rs stored the resulting sentence in a String at start of serving. term.rs never set ENABLE_VIRTUAL_TERMINAL_INPUT. The picker toggled on Enter and cleared its ticks on entry. serve.rs printed the address before PORT80 was set.

## After

dhcp::supervise() owns the decision on a 3s loop and hands the front ends an Arc<Mutex<String>> they re-read every frame (TUI) or on change (CLI). net::connected_addresses() filters local_addresses() by membership in ipconfig / `ip -4 -o addr show up` / ifconfig output. net::live_default_gateway() filters default_gateway() by membership in `arp -a`. 98 tests pass. Verified unattended with wifi genuinely off: servers up in ~5s, gorilla.local resolves, page serves 200 under all three names, captive probe gets 302, far end reachable and serving.

## Known Alternatives

For the gateway, my first attempt was 'a gateway with no routable address behind it is not a router'. Rejected because the existing test we_refuse_to_answer_where_a_router_exists failed against it, correctly: a host plugged into a live network that has not yet been granted an address has no routable address either, and is exactly the host that must not be served DHCP. The neighbour-table check answers the same question without opening that hole.

For connectivity detection, parsing ipconfig's 'IPv4 Address' label was rejected on the project's existing grounds, quoted from net.rs: parsing tools by label 'depends on the console language of the machine, which is a bad thing to depend on in Kabul or Bamako'. GetAdaptersAddresses via FFI was considered and set aside as more struct-layout risk than the membership test needs.

For mDNS, cargo-zigbuild-style external crates are not available: this project has no dependencies by rule, so SO_REUSEADDR is set by hand-rolled FFI in the same shape as the existing console code in term.rs.

## Decisions Made

- 📄 **Re-evaluate the guard on a loop instead of once at startup** — 'the verdict had been reached seconds earlier and nothing was going to look twice'. Advice a person acts on has to be advice the program will notice them acting on.
- 📄 **Test addresses for membership in a platform tool's output instead of parsing its labels** — net.rs already refuses label parsing on the grounds that it 'depends on the console language of the machine, which is a bad thing to depend on in Kabul or Bamako'. Membership needs no word.
- 📄 **Establish a router by the neighbour table, not by the presence of a gateway or an address** — Measured: 'wifi up 10.29.128.1 00-fe-ed-c0-ff-ee dynamic / wifi off gone'. The danger is a live router, so test for one.
- 📄 **Reject 'a gateway with no address behind it is not a router'** — The existing test failed against it, correctly: a host on a live network awaiting its first lease has no routable address and must not be served DHCP.
- 📄 **Enter adds a tick and never removes one** — 'it made the reflex key the destructive one'. One key adds, one key removes, and the key people press without reading cannot lose work.
- 📄 **Forget the selection when a transfer ends, but not while moving inside the picker** — Ticks surviving movement was requested and is right; surviving a completed transfer sent a private document. The two were not separated.
- 🤖 **Run the offline verification unattended and read the log** — The reporting machine is the machine under test, and its only channel to me is the connection being switched off, so any check made afterwards describes a state that no longer holds.

## Tried and Abandoned

- **netsh wlan disconnect to reproduce the wifi-off condition** — Does not release the address. Verified over 22 seconds: Get-NetIPAddress still reported 10.29.136.94 and a UDP socket still selected it. Needed `ipconfig /release` as well, which is itself the discovery that explains the whole fault.
- **Concluding from the machine's live state that the guard was correct** — The owner can only send a message over the wifi being switched off, so the state I observed was always going to show it connected. The WLAN-AutoConfig event log gave the real window: disconnected 09:34:52, reconnected 09:39:33.
- **cargo-zigbuild for the Linux target** — Its proc-macro dependencies need an MSVC host toolchain that is not installed. zig is invoked directly as the linker instead, which works because this crate has no build scripts of its own for that target, no proc-macros and no C dependencies.
- **term::leave()/enter() around the firewall fix in the TUI** — No such API: term::Raw is an RAII guard with no suspend. open_ports() returns a Result and each front end presents it.

## Technical Debt

🟢 **RESOLVED** — The offline verification lived in a scratch PowerShell script outside the repository. It is now bench/cable/, with offline-guard-test.ps1, far-end-test.ps1, recorder.py and a README explaining why each restores the network in a finally block and registers a reconnect task first.
🟠 **MEDIUM** — connected_addresses() and live_default_gateway() each spawn a subprocess per supervisor cycle → Two processes every three seconds while serving. Acceptable on the machines measured; on a 2012 laptop under load it is worth caching for a cycle or moving to GetAdaptersAddresses via FFI.
🟠 **MEDIUM** — The DHCP guard still has a window → A host on a live network before its first lease has no routable address and no neighbour entry. Consider also refusing when any non-cable interface reports carrier.
🟠 **MEDIUM** — No integration test for the cable path → Beacon and find_peer against each other over loopback would cover discovery; a two-process harness in bench/ would cover the rest.
🟡 **LOW** — Request.requested (DHCP option 50) parsed and never used → Honour a client's requested address when free, or drop the field.
🟡 **LOW** — tune::reachable() returns None on everything but Windows → Probe ufw/firewalld/nft. Reporting 'cannot tell' is honest but leaves Linux without the most useful diagnostic.
