# Handover: what the Linux side has to settle, and why it is asked for

This is the note that went down the cable to the machine on the other end,
kept here because the questions in it are not answered yet and whoever picks
this up next needs to know which claims in this release are measurements and
which are arguments.

The short version: **0.9.0 was written and tested entirely on Windows.** The
Linux artifact it publishes has never been executed. Not on a developer
machine, not in CI, not once. Everything below follows from that.

## Where this stands

The cable path works. Two laptops, one CAT cable, no router, no switch, no
wifi between them. The Windows machine holds 169.254.87.61 and serves; the
Debian machine was given 169.254.87.1 by the hub's own address server and
answers ping in under a millisecond. About 94 MB has crossed, so the data path
is not in question.

What is in question is everything that can only be observed from the far end.

## What was sent over, and why each thing

### The binary itself

`hub-0.9.0-linux-x86_64-static.tar.gz`, 461,059 bytes, sha256
`686e3b5f328fb4a7d0b7f18cc7171ff534554f016f73f6a486615e6da2ff4680`. This is
byte-identical to the published release asset — deliberately, so that running
it answers a question about the thing people will actually download rather
than about a convenience build.

It is cross-compiled from Windows with zig as the linker, targeting
`x86_64-unknown-linux-musl`, statically linked. It has been verified only as a
structurally correct ELF: 64-bit, x86-64, `EXEC`, no interpreter, no Windows
resource section. That is a statement about the file's shape and says nothing
about whether it runs.

Two code paths in it have therefore never executed anywhere:

- `tune::detect_linux()` reads `/sys/class/net/<if>/speed` and `operstate` to
  size the transfer buffer. If it misreads the interface, transfers run at the
  wrong chunk size and nothing says so.
- `net::connected_addresses()` shells out to `ip -4 -o addr show up` and tests
  the addresses we hold for **membership** in that output. Membership rather
  than parsing, because field labels are translated on a system installed in
  another language and this program is meant for Kabul and Bamako as much as
  anywhere. That reasoning has never been checked against a real `ip` on a
  real distribution.

`hub doctor` exercises both, which is why the full output of it is worth more
here than a passing test.

### The briefing, as a plain text file

Asked for as `.txt` and served alongside the binary, because the receiving
machine has no internet and pasting a long document between two laptops that
share only a cable is otherwise a retyping exercise. This is the same reason
the whole project exists.

## The four things only that machine can answer

**1. Does the binary run at all.** `./hub --version`, then `./hub doctor`, and
the doctor output verbatim including anything it gets wrong about the machine.

**2. Does `cable-get` find the sender with nothing typed.** The receiving side
listens for a beacon on UDP 42424 rather than being told an address. This is
the whole answer to the owner's objection to 0.9.0's first cut — *"I had to
type the whole 169.254.87.61, not exactly easy and convenient"* — and it has
only ever been tested against a sender on the same machine.

**3. Do the five checksums match.** This closes the 45 MB claim, which is
currently an argument: it was measured on an earlier build, and the code that
moves the bytes has not been touched since. That is a reasonable inference and
it is not a measurement, and this project labels the difference.

**4. Did anything appear on the desktop by itself.** Every dependency is
verified from the Windows side: the resolver answers the probe name
`nmcheck.gnome.org`, and that probe receives an HTTP 302, which is the
redirect that should make a desktop raise "Sign in to this network". Whether
GNOME then raises it is visible only from that chair. `nmcli networking
connectivity check` reporting `portal` would mean the mechanism works and only
the prompt is missing; `limited` or `none` would mean the probe is not
reaching us at all.

A plain "nothing appeared" is a result. It is the result this release most
needs and cannot get any other way.

## The one instruction that is not negotiable

The address server must never run on a network that has a router. A second
thing handing out addresses can take a school or an office offline. The guard
refuses unless it can see it is on a bare cable, and there is an
`--addresses-anyway` override.

**The far end was told not to use it.** If the guard refuses, the refusal is
the finding. Working around it produces a test that proves the program can be
made to do the dangerous thing, which was never in doubt.

The override is in use on the Windows side for one specific reason worth
recording: the owner's wifi has to stay on for them to be reachable at all,
so the guard correctly refuses and the override is the only way to test the
rest. That is a developer's exemption, not a normal path.

## Why negative reports are asked for explicitly

Five real faults in this release were found by a person using the program and
saying "this does not work". None were caught by the 98 tests. Two of them —
the arrow keys never having worked on Windows in any released version, and
SEND THE 1 TICKED appearing to do nothing while doing everything — were
invisible to a test suite because the program was behaving correctly and
communicating badly.

So the far end was asked for whatever was confusing, badly worded or looked
broken, and told that kind of report is worth more here than a green run. See
[0.9.0-WHAT-CHANGED-PART-2.md](0.9.0-WHAT-CHANGED-PART-2.md) for what that
class of report has already been worth.

## Still open after this

Whether `gorilla.local` or the raw address was typed for the 94 MB. It matters:
the name was typed successfully once, on a build where it resolved through the
DHCP-advertised resolver rather than through multicast. Nobody has typed it
since mDNS was added, so the path that works when the guard refuses — which is
the path that matters on any machine that also has wifi — is untested by a
human.

The remaining items, with what each one blocks, are in
