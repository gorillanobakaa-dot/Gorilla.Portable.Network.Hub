# 0.9.8 — developer notes

Removing one entry from a list of two lines, and why that needed a controlled
experiment rather than a judgement.

Written on the Windows laptop, 2026-09-08.

---

## What was open

0.9.7 shipped `HOTSPOT_SERVICES` with three entries and said, in its own notes
and on its own release page, that the third was a judgement call:

> **`WFDSConMgrSvc` is a judgement call, not evidence.** It is not a declared
> dependency. Windows 11's hotspot is built on Wi-Fi Direct and this service is
> Wi-Fi Direct's connection manager, which is why it is listed — but nobody has
> established that hotspot fails with the first two enabled and this one off.

The 0.9.7 measurement made it worse rather than better: it set **all three** to
`Manual` and proved the *set* worked, which proves nothing about any member of
it. It did observe that `WFDSConMgrSvc` never left `Stopped`, which is evidence
against it but not proof — a service can be started on demand by something
else, and "it was not running when I looked" is a weaker claim than it sounds.

## The experiment

`bench/hotspot-service-isolation.ps1`. One variable moved:

```
icssvc          Disabled -> Manual
SharedAccess    Disabled -> Manual
WFDSConMgrSvc   left Disabled and Stopped
```

Result:

```
== STATE UNDER TEST ==
  icssvc          Start=3  Running   Manual
  SharedAccess    Start=3  Stopped   Manual
  WFDSConMgrSvc   Start=4  Stopped   Disabled

== CAN WINDOWS CONFIGURE A HOTSPOT? ==
  manager created: YES
  ssid: 'WIN-VR6KGAH3RAF 5437'   passphrase length: 8   band: Auto

== DOES IT ACTUALLY START? ==
  operational state: On
  adapters up: Wi-Fi, Ethernet, Local Area Connection* 2
  virtual access point present: True

VERDICT for WFDSConMgrSvc: NOT NEEDED - the hotspot started with it left Disabled
```

**Configurable was not accepted as the answer.** `TetheringOperationalState`
could in principle report optimistically, so the script also checks for the
virtual access point as its own network adapter. `Local Area Connection* 2` is
that adapter. A hotspot that is only claiming to run does not get one.

Restored cleanly this time — all three back to `Start=4` and `Stopped`, wifi
still connected — because the `$started` flag is now set *before*
`StartTetheringAsync()` rather than after it reports success. That was the
0.9.7 script's bug and it is why the fixed version lives in the repository.

## The change

`HOTSPOT_SERVICES` is `[(&str, &str); 2]`.

**This is not tidying, and the distinction matters.** A message that names three
services when two are the problem has three costs, in increasing order:

1. one more line for somebody to type
2. one more thing changed on a machine that did not need changing
3. **the evidence of which change mattered is destroyed** — the person who
   fixed it cannot say, and neither can whoever looks at that laptop next

The third is the one that justifies the work. It is the same argument the
existing test `the_advice_does_not_name_services_that_are_fine` already makes
about *filtering* the list, applied to the *contents* of the list. Both come
from the same place: a diagnostic that over-reports is not being cautious, it is
being unfalsifiable.

## The guard

```rust
#[test]
fn the_list_holds_only_services_measured_to_matter() {
    assert_eq!(HOTSPOT_SERVICES.len(), 2, "a service was added without a measurement");
    assert!(!HOTSPOT_SERVICES.iter().any(|(s, _)| *s == "WFDSConMgrSvc"), ...);
    ...
}
```

It exists because **the argument for putting `WFDSConMgrSvc` back is more
persuasive than the argument for leaving it out.** "Windows 11's hotspot is
built on Wi-Fi Direct" is true, sounds decisive, and will occur to the next
person who reads this code — probably me. An argument like that is beaten by a
measurement, and the measurement needs somewhere to live that a future reader
cannot walk past. Anybody adding a third entry has to delete this test and say
why.

## The whole of 0.9.7's advice, now measured

Three runs, and the A/B/A is the point:

| run | services at Manual | tethering manager | hotspot |
|---|---|---|---|
| before anything | none | `0x83120001` | — |
| all three | icssvc, SharedAccess, WFDSConMgrSvc | created, SSID readable | **On** |
| restored | none | `0x83120001` | — |
| two only | icssvc, SharedAccess | created, SSID readable | **On** |
| restored | none | `0x83120001` | — |

`0x83120001` from `CreateFromConnectionProfile` **is** the red bar in Settings.
The window has nothing to populate its boxes from, so it reports the only thing
it knows: "We can't set up mobile hotspot." That is why the test asks the API
rather than reading the window — it gets the same failure the window is
reporting, as a value, in a script.

### `SharedAccess` never ran, in any run

Set to `Manual`, stayed `Stopped`, through two successful hotspot starts. It has
to be *startable*, not started. The advice asks for `Set-Service` on it and
`Start-Service` only on `icssvc`, which was right by accident in 0.9.7 and is
right on purpose now.

Worth stating plainly for anyone auditing what this tells people to do: after
following the advice, **nothing is left running that was not running before**.
One service is started, `icssvc`, and only because the tethering manager cannot
be built without it.

## What the scripts are for

Both are in `bench/`, not in a temp directory, and both follow `bench/cable/`'s
shape: capture the before-state rather than assume it, work inside a `try`,
restore inside a `finally`, and verify the restore independently afterwards
rather than trusting the script's own summary.

- **`hotspot-services-test.ps1`** — does the advice work at all
- **`hotspot-service-isolation.ps1`** — is each service in it actually needed

The second is the template if another service is ever proposed. Change one
thing.

## ⚠ Claimed but not verified

- **One machine, one Windows build.** Everything here was measured on a single
  Windows 11 laptop with an Intel Wi-Fi 6 AX201. `WFDSConMgrSvc` not being
  needed is now measured *here*; a different radio or a different Windows build
  could in principle differ, and nobody has tested one.
- **The localisation argument is still reasoned, not measured.** `REG_DWORD` not
  being translated is documented behaviour, but no non-English Windows was
  available. The test carries a sample instead of a machine.
- **Four cable behaviours** from the 26-09-08 Debian handover remain unrun on
  Windows — the `gorilla.local` collision refusal, the promise when there is no
  collision, the receive list naming the other machine over `/?who`, and the QR
  on a cable. They need the second laptop.
- **The Arch package has still never been installed** by anybody.
