# Version 0.9.0: the Hub can now use a cable, and nothing it could already do was lost — Plain Language

> Session record generated 2026-09-06

---

## What happened

Until now this tool had one way to move files: over wifi. That is the right answer in most rooms and the wrong answer in more rooms than you would think. A staffroom at four o'clock has thirty phones and a microwave oven all using the same slice of radio. A school in a valley has a wifi card that stopped working in 2019 and no budget to replace it. Thirty gigabytes of video over an old wifi connection takes most of an afternoon. An ordinary network cable, the kind that costs about two pounds, has none of those problems and is roughly ten to a hundred times faster.

The difficulty is that two laptops joined by a cable have no router between them, and a router normally does two invisible jobs. It gives each computer an address, and it lets each computer find the other. Without those two things the cable is a piece of plastic. Windows and Mac computers eventually work around the missing router on their own, after waiting thirty to sixty seconds. Most computers running Linux do not: they wait for a router that will never answer, forever, and the cable never starts working at all. That is not a rare edge case. It is what happens every time somebody plugs a Debian or Ubuntu laptop into a Windows one, which is exactly what the owner of this project was trying to do.

This version teaches the Hub to do those two router jobs itself, for the length of one transfer, and then stop. It also does something equally important that is quiet enough to overlook: it adds all of this without removing anything. The version this work was based on had been rebuilt from scratch by a different AI, and that rebuild had quietly deleted the on-screen dashboard, the live list of connected devices, the join-by-camera QR code, and the ability to show devices by name. Those are the features the project's own release page advertises with screenshots. This release keeps every one of them and adds the cable alongside.

## Honest state of play

Finished and proven by running it: the cable discovery, the address server, the speed matching, the four-item dashboard, the firewall checker, and the security repairs. Seventy automated tests pass. A Linux program file has been built and confirmed to be a genuine, self-contained Linux program that will run on any distribution without installing anything alongside it.

Finished but NOT yet proven by use: the actual cable transfer has not been re-run end to end since the merge. The owner's successful Windows-to-Debian transfer was done with the earlier rebuilt version, not with this one. The code paths are the same in design but they are not the same code, and saying otherwise would be dishonest.

Not yet done at all: the Linux program has not been run on a Linux machine, because this work was done on a Windows one and a Windows computer cannot run a Linux program to check it. The Debian and Arch installer packages have not been rebuilt for this version.

Not touched: everything the wifi side of the tool already did. It was deliberately left alone.

## Worst case if something is wrong

The most harmful thing that could go wrong is the address server misbehaving on a network that already has a router. If the Hub handed out addresses inside a school that already has its own network equipment, it would compete with the school's router and could knock every computer in the building off the network, not the two involved in the transfer. That is a genuinely serious outcome and it is why the feature refuses to start unless it can see clear evidence that it is on a bare cable with no router present. It also never starts unless a person deliberately chose a cable transfer.

A second, smaller risk: because the cable transfer has not been re-tested since the merge, it is possible that something in the joining-together broke it in a way the automated tests do not cover. The symptom would be the receiving computer saying it found nothing, or the transfer stopping partway. Nothing would be damaged or lost; it would not work, and you would be back to using wifi or a memory stick until it was fixed.

## What changed for you

**Moving files between two laptops**
- Before: Only over wifi. If the wifi was congested, broken or absent, there was no other way.
- After:  A cable works too. Plug it in, run one command or pick one menu item, and the files move at the speed of the cable.
- Affects: everyone

**Plugging into a Linux computer**
- Before: The Linux computer waited forever for an address and the transfer timed out. Nothing on screen explained why.
- After:  The sending computer gives it an address in about half a second. Nothing is typed on either machine.
- Affects: everyone

**Finding the other computer**
- Before: You had to read a numeric address off one screen and type it into the other, correctly.
- After:  The sending computer announces itself once a second. The receiving one finds it. No numbers are read or typed.
- Affects: everyone

**The on-screen dashboard**
- Before: Two choices: hand out files, or get files.
- After:  Four choices: hand out over wifi, send down a cable, get from another computer, and check this computer. The cable form hides the wifi questions, because on a cable there is no network to name and no password to set.
- Affects: everyone

**When nothing can reach the computer**
- Before: The most common failure was a firewall silently blocking connections. Every diagnostic line still read as healthy, so it looked like the program was broken.
- After:  A 'Check this computer' screen says plainly whether the firewall is blocking, and one keypress opens the ports.
- Affects: everyone

**Speed on a fast cable**
- Before: Files were always moved in fixed-size pieces, tuned for wifi.
- After:  The piece size is matched to the actual speed of the cable, from small pieces on a slow link up to large ones on a very fast link.
- Affects: some users

**Security of the file sharing**
- Before: The rebuilt version this work drew on had a hole: any device on the network could read any file on the whole computer, not the shared folder. We confirmed this by exploiting it.
- After:  That hole does not exist here. We confirmed that too, by trying the same three attacks against the new build and getting refused every time.
- Affects: everyone

## What you can do now

- Move files between two laptops using an ordinary network cable, with no router, no wifi and no internet anywhere.
- Do that even when the other laptop runs Linux, which previously did not work at all and gave no explanation.
- Find the other computer without reading or typing any numeric address.
- Choose all of this from the on-screen menu instead of typing commands, which is the point: very few teachers or children will drive a command-line tool.
- Ask the program plainly whether a firewall is blocking it, and fix that with one keypress instead of hunting through Windows settings.
- See what speed of cable is plugged in and what size pieces the program has chosen as a result.
- Keep using every wifi feature exactly as before: the live list of devices, the join-by-camera code, the handed-in work, the class page. Nothing was traded away.

## What is still missing

- **An end-to-end cable transfer using this build** — We can say the parts work and the tests pass, but we cannot yet say 'we moved a real folder down a real cable with this exact program'. Until someone does, that claim is not ours to make.
- **Running the Linux program on an actual Linux computer** — The Linux file has been built and inspected and is structurally correct, but nobody has run it. If something is wrong with it, you would find out on first use and not now.
- **The Debian (.deb) and Arch installer packages for this version** — Linux users get a single program file to run and not a package that installs itself into the system menu. It works; it is less tidy than the previous release was.
- **Giving out addresses on Linux without administrator rights** — If you send from a Linux computer to another Linux computer, you may need to run it with sudo, or the far end may need its address set by hand. Sending from Windows or Mac is unaffected. The program says this in plain words and does not fail silently.

## How to check that what we say is done actually works

**Step 1:**
```bash
On the Windows computer, open a terminal where the program is and run: hub doctor
```
  - **Pass:** It prints 'hub 0.9.0'. If a cable is plugged in, there is a line starting 'cable' naming your adapter and its speed, and a line saying whether other devices can reach this computer.

**Step 2:**
```bash
Run: hub
```
  - **Pass:** A screen appears offering four choices, the second of which is 'Send files down a cable to one other computer'. Arrow keys move between them.

**Step 3:**
```bash
Choose 'Check this computer' and read the 'reachable' line.
```
  - **Pass:** It says either that other devices can get in, or that they cannot and offers to fix it. If it says they cannot, press enter on the fix and approve the Windows permission prompt.

**Step 4:**
```bash
Plug a network cable between the two laptops and wait half a minute. On the sender run: hub cable <your folder>
```
  - **Pass:** It prints the folder name, the cable speed, that it is announcing itself, whether it is giving out addresses, and a web address beginning http://169.254.

**Step 5:**
```bash
On the receiving laptop run: hub cable-get
```
  - **Pass:** Within about a minute it says 'Found <name> at <address>' and then lists each file as it arrives. This is the step that has not yet been done with this build, so this is the one that matters most.

**Step 6:**
```bash
As a fallback, open the http://169.254... address the sender printed in any web browser on the other laptop.
```
  - **Pass:** The class page appears with the files on it. If this works but step 5 does not, the problem is in the automatic finding, not in the transfer itself.


## Should you be concerned?

Not about the security of this build. The two serious holes that existed in the version this work was based on were confirmed by attacking a running copy, and then confirmed closed by attacking this one the same way. Any device on the classroom wifi could previously have read private files anywhere on the teacher's computer; it cannot now.

You should hold one claim loosely: that the cable transfer works. It very probably does, the design is unchanged and the parts are tested, but it has not been run end to end with this exact program, and the difference between 'should work' and 'was seen to work' is the whole reason this project keeps documentation like this. Test it before relying on it in front of a class.

One thing genuinely deserves care and not concern. The address-giving feature does real damage in the wrong setting: on a school network that already has its own equipment, a second thing handing out addresses can disrupt the whole building. It has been built to refuse in that situation and it checks before acting. But if you ever see it say it is handing out addresses while you are plugged into a school or office network instead of a bare cable between two laptops, stop it and report that, because it would mean the safety check was wrong.

Finally, be aware of what this release deliberately did NOT do. It did not adopt the rebuilt version wholesale, because doing so would have silently deleted the dashboard, the device list and the QR code that your own release page advertises. If you were expecting the smaller, simpler program from that rebuild, this is not it, and that is on purpose.

## Glossary

**CAT cable, or network cable** — The rectangular-plugged cable that connects a computer to a wall socket or router; the same cable works directly between two laptops.

**Router** — The box that normally sits in the middle of a network, gives every device an address, and passes messages between them.

**DHCP** — The conversation in which a computer asks 'what is my address?' and something on the network answers. With no router, nobody answers.

**Link-local address** — An address beginning 169.254 that a computer gives itself when nothing else will give it one. Seeing one is a reliable sign that there is no router present.

**Firewall** — The part of the operating system that decides which incoming connections to allow. When it blocks this tool, everything looks healthy and nothing works.

**Static binary** — A program file that carries everything it needs inside itself, so it runs on any version of Linux without installing anything first.

**Directory traversal** — A trick where a web address containing '..' escapes the shared folder and reaches private files elsewhere on the computer. This is the hole that was found and closed.

**Lease** — A temporary loan of an address, given out with an expiry time so it can be reused later.
