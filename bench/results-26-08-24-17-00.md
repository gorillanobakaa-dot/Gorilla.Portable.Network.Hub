# The afternoon: LocalSend measured, and the design decided

Second half of 2026-08-24. The first half (`results-26-08-24-12-20.md`) measured
the radio. This half measured the software, and three findings changed the
design rather than confirming it.

Evidence tags as elsewhere: **[measured]** on this hardware today,
**[source]** read out of the LocalSend 1.18.2 tree, **[inference]** reasoning
from those, to be treated as a hypothesis.

---

## 1. The headline: it works, end to end, with no infrastructure

**[measured]** LocalSend moved a **4.0 GB file at 6.1 MB/s** between two laptops
over a hotspot created by the Sony VAIO. No router, no internet, no
infrastructure of any kind in the room.

Timeline, from `hostapd.log` and the receiving screenshot:

```
15:41:30  ThinkPad completes WPA handshake on BURST_NET
15:45:45  transfer starts (inferred from 77.4 MB at 15:46:52)
15:57:36  transfer FINISHES, 4.0 GB, 6.1 MB/s, no errors
15:58:09  systemd SIGKILLs hostapd
```

The transfer finished **33 seconds before the access point died**, which is the
only reason this is a result rather than a near miss. No disconnect was logged
for the client in that window.

6.1 MB/s is the radio's ceiling, not LocalSend's: a browser got 5.5 to 6.0 over
the same link and the per-second sampler measured a 6.16 mean. **TLS, the
SHA-256 pre-pass and the absence of hardware SHA on Ivy Bridge cost nothing
measurable.**

### A wrong conclusion, recorded rather than quietly fixed

The first reading of this was that the transfer had gone over the office wifi,
because by the time it was examined the card was back in client mode on
`the office network`. That was **state after the fact mistaken for state during**.
The hostapd timestamps settled it. Look at the timeline, not the aftermath.

## 2. LocalSend needs no internet. Not "only for the optional path", none

**[source]** The WebRTC path is **compiled out**, not optional:

```dart
// app/lib/provider/network/webrtc/signaling_provider.dart:22
/// WebRTC (and therefore the signaling connection) is disabled for now.
const webRTCEnabled = false;
```

That constant is the sole guard on `SetupSignalingConnection()` at
`init.dart:222`, and the analyser marks the block dead code. So
`wss://public.localsend.org` and `stun.localsend.org` are strings that nothing
can reach in 1.18.2.

Also **[source]**: there is no update check (the only "update" hit in the
settings screen is a comment about a text field); every external URL is a
`launchUrl` that opens the user's browser on a tap; and the only `https://`
strings in `packages/core/src` are unit-test assertions against `192.168.1.1`,
`[::1]` and a link-local address.

### Correction to an earlier atom

The brain atom from the 2026-08-22 read says internet is needed "ONLY for the
opt-in WebRTC cross-network path". **That is wrong in a way that matters: it is
not opt-in, it is disabled at compile time.** Nothing in 1.18.2 dials out.

### But it needs a NETWORK, which is a different thing

It cannot create one. No AP, no Wi-Fi Direct, no ad-hoc anywhere in the tree. It
opens a socket, joins a multicast group and waits for peers on a network it
assumes exists. That distinction is the whole reason this project exists.

## 3. LocalSend cannot resume, and it costs a factor of two hundred

**[source]** Three facts that together explain everything else:

```
Range / 206 / seek in the core : NONE
                                 (the only "range" hits are a multicast IP-range
                                  comment and test fixtures called "Nice Orange")
receiving a file               : tokio::fs::File::create(&path)   <- TRUNCATES
MAX_UPLOAD_ATTEMPTS            : 3, and only for SaveResult::HashMismatch
```

**[measured]** Same program, same two machines, same file:

| link | speed | outcome |
|---|---|---|
| flapping every 16 s | **30.6 KB/s** | 1.1 MB of 4 GB, 36 hours estimated |
| stable | **6.1 MB/s** | 4.0 GB complete |

**[inference]** The arithmetic: at 6 MB/s, sixteen seconds moves about 96 MB.
The connection dies, the destination is recreated at zero bytes, and it starts
again. Net progress across the period, essentially nothing.

A browser survived the identical link because it issues HTTP Range requests and
resumes. **One tool banks the 96 MB, the other throws it away. That is the entire
difference between 6 MB/s and 30 KB/s.**

### Why this reframes the carousel

This is not a criticism of LocalSend. On a stable home network, truncate-and-
restart is a reasonable simplification.

In a classroom it is fatal, and it fails in a disguised way: it looks like
slowness when it is amnesia.

The fountain code was being described as loss tolerance. **It is bigger than
that: it is what makes progress durable on a link that comes and goes.** A
receiver keeps every symbol it ever heard, needs no particular ones, and
finishes on a later lap. Nothing restarts and nothing is requested.

The same property is what makes the village case work at all: with RaptorQ,
**any symbol any device holds is useful to any other device**, with no
negotiation and no piece map. Two children with partial copies can combine
without either knowing what the other has.

## 4. Windows abandons an offline network in sixteen seconds

**[measured]** From `hostapd.log`:

```
15:06:27  CONNECTED
15:06:43  DISCONNECTED     16 s
15:06:43  CONNECTED
15:06:59  DISCONNECTED     16 s
15:07:03  CONNECTED
15:08:08  DISCONNECTED
```

**[measured]** The mechanism, from a packet capture: the client repeatedly
resolves `dns.msftncsi.com` and tries `www.msftconnecttest.com`. That is the
Network Connectivity Status Indicator. With no NAT it fails, Windows marks the
network dead, and leaves for a remembered one.

This produced three symptoms that all looked like other faults: a LocalSend
transfer at 30 KB/s, `ConnectionRefused` on `10.42.0.1:53317` that looked like a
firewall (LocalSend was listening correctly on `0.0.0.0` throughout, the station
simply was not there), and browser downloads dying with "network issue".

**Fix, verified working:** resolve the probe domains to the AP and answer
`/connecttest.txt` with the exact body `Microsoft Connect Test`. See
`wifi-ap-lab/ncsi-responder.py`.

**This is a hard requirement for anything deployed to a classroom.** A burst
network never has an upstream, so without this every Windows client wanders off
mid-transfer.

Related **[measured]**: this kernel cannot NAT at all.
`CONFIG_NF_TABLES_IPV4` and `CONFIG_IP_NF_IPTABLES` are both unset, so there is
no iptables and no nftables for IPv4. Answering locally is not a shortcut, it is
the only option here.

## 5. The 54 Mbps broadcast ceiling is the protocol, not the card

This corrects an assumption that was shaping the design.

802.11 requires group-addressed frames to use a rate from the BSS **basic rate
set**, and that set is legacy OFDM only, topping out at **54 Mbps in every band
on every card ever made**. A Wi-Fi 7 radio with 320 MHz channels and four spatial
streams still broadcasts at 54 Mbps.

So `basic_rates=540` is not "the best the AR9485 can manage". It is the ceiling
of that mechanism, permanently.

**[inference]** Which splits how better hardware helps:

| | scales with a better card? |
|---|---|
| unicast transfers | fully |
| broadcast via `basic_rates` | **no, 54 Mbps forever** |
| broadcast via raw injection | fully, the rate is ours to choose |
| band and channel choice | hugely, 5 and 6 GHz are far emptier |
| client count, compression, fountain coding | yes |

**Raw injection is therefore the only path by which better hardware makes the
classroom faster.** It was Mode B in `03-design-burst-carousel.md`, demoted in
that same session to "optimisation, not feasibility". **This promotes it back.**

**[measured]** The Sony can do it: `iw phy` advertises both `monitor` and
`outside context of a BSS`.

## 6. Language decided: Rust

**[measured]** Same program in both, fixed-response HTTP listener plus config
write plus supervised child. Go with `-s -w -trimpath`, Rust with
`opt-level="z"`, LTO, one codegen unit, `panic=abort`, stripped. No crates.

| | raw | gzip | xz | at 8 KB/s |
|---|---|---|---|---|
| Go | 2,289,956 | 981,802 | 799,496 | 1.6 min |
| Rust | 352,464 | 176,088 | 148,144 | **0.3 min** |
| | 6.5x | | 5.4x | |

**Size alone did not decide it.** 1.6 minutes is not cruel. The deciding factors:

1. **RaptorQ.** Rust has the `raptorq` crate, a faithful RFC 6330 implementation.
   Go's equivalents are hobby-grade. This is the difference between using a
   library and writing one.
2. **No GC on the weakest receiver.** Fountain decoding a multi-gigabyte stream
   is sustained allocation-heavy work, and the target receivers have 4 GB.
3. **LocalSend's core is already Rust.** Same language as the thing we complement.
4. **Go's 2.18 MB is a floor**, always present. Rust's 352 KB grows with what is
   written.

**[measured]** Windows is not an obstacle: `x86_64-pc-windows-gnu` and mingw were
already installed, and the cross-build produced a working 324,608-byte PE32+
that runs under Wine. **Smaller than the Linux build.**

Go would have won on cross-compilation convenience only.

## 7. Kernel bypass ruled out, with numbers

DPDK, Seastar and TRex were considered. **[measured]** on this 2012 laptop,
through the full kernel TCP stack:

```
loopback throughput   379 MB/s  =  265,028 packets/sec
what wifi demands     6.3 MB/s  =    4,404 packets/sec
CPU idle today                       94%
```

**The kernel already delivers sixty times what the radio can carry, at 94%
idle.** There is no overhead to remove.

More fundamentally: **DPDK does not support wifi and cannot easily.** It is
poll-mode drivers for Ethernet NICs. Association, WPA2 key management, rate
adaptation, retries and aggregation live in `mac80211` and card firmware. Bypass
that and you are not a wifi device.

The bottleneck is **airtime**, which is physics and protocol, not software.

**The instinct was right about the wrong layer.** The thing worth bypassing is
the 802.11 association-and-acknowledgement machinery, and that is raw injection.
The one technique worth borrowing from those projects is batching (`sendmmsg`,
`AF_PACKET` with `TPACKET_V3` rings) if injection ever runs at hundreds of
Mbit/s, which is still six times inside what this laptop already does unaided.

## 8. Process lessons, all three variants of one trap

**A cleanup handler cannot protect what kills it.** Three lockouts today, each a
different escape:

1. `trap ... EXIT` in a bash script. The harness killed the shell, the trap never
   ran, and this machine's **only** interface was left unmanaged. Twice.
2. Fixed with a **systemd transient timer**, armed before the radio is touched,
   owned by PID 1. That worked, and has fired correctly since.
3. But `hostapd -B` still died at 15:58:09:
   `app-com.anthropic.Claude-2554.scope: Killing process 51884 (hostapd)`.
   **Daemonising does not escape the calling session's systemd scope, and neither
   does `setsid nohup`.** Only a separate unit does.

Now fixed: `hostapd`, `dnsmasq` and the file server all run via
`systemd-run --unit=...`, verified in `/system.slice/`, and proven to survive the
shell being killed.

**Generalisation, well beyond wifi:** any operation that removes the machine's
own access to something must have its recovery owned by a longer-lived
supervisor than the actor. Ask "if this process is SIGKILLed right now, what
puts it back?" If the answer is code inside that process, there is no answer.

Smaller ones from the same day:

- **`sudo -n timeout N tcpdump -w f.pcap` does not stop tcpdump.** It ran forty
  minutes and produced a 64 MB capture that then hung `tshark -V`. Bound by
  packet count (`-c`), which self-terminates.
- **`timeout` exits 124 when it succeeds**, so `if ! sudo timeout ...` treats
  every successful full-length capture as a failure.
- **A monitor interface hears the whole channel.** Filtering on
  `wlan.fc.type == 2 && wlan.da[0] & 1` caught two neighbours' broadcasts and
  produced a result contradicting 802.11. Filter by transmitter first.
- **An AP with no associated station transmits no broadcast**, so the multicast
  tool looks broken and is not.
- **`sudo cp` then `cat >>`** silently restarts hostapd with the untuned file
  while every log line says success.
- **`iw dev <ap> station del`** is a deauthentication frame and gets blocked as
  an attack even when it is the AP's own administrator.
- **An association request is a negotiation; a probe request is a boast.** A
  client advertised one spatial stream and no HE to our AP while its probe
  requests carried `Rx Bitmask 8-15 = 0xff` and an HE capability element. The
  tell that the association frame was tailored: it claimed one stream while also
  claiming `Tx STBC`, which needs two or more transmit chains.

## 9. First code written

`wifi-ap-lab/fileserver/`, Rust, no dependencies, **388,744 bytes**.

A static file server with **byte-range support from line one**, because that is
the property whose absence cost LocalSend a factor of two hundred this
afternoon. Verified: 206 with correct `Content-Range` and byte-exact content,
suffix ranges, open-ended ranges, 416 on unsatisfiable, 403 on path traversal.

It exists because `python3 -m http.server` spawns one OS thread per connection,
and a 400-connection test on an Ivy Bridge chip would have measured Python's
scheduler rather than the radio. This uses a bounded 64-worker pool.

**A bug the tests caught:** `bytes=` was stripped twice, once by the header split
on `=` and again in `parse_range`, so every valid range parsed as `None` and
every resumed download got a 416. The one test this program exists to pass is
the one that caught it.

## 10. What is still open

1. **The multicast DATA rate.** Beacons were measured at 1, 12, 24, 36 and 54
   Mbps. Group-addressed **data** frames were never confirmed, because an AP with
   no associated station transmits none. 802.11 requires both to use the basic
   rate set, so they are expected to match, but this is **[inference]**.
2. **Delivered broadcast throughput and range**, with real receivers, at
   distance, through bodies. Nothing here measured that.
3. **Many-client behaviour.** Everything today was one or two clients. The
   `axel -n 400` test is staged and not yet run, and even that measures many
   connections rather than many stations.
4. **Whether a phone's built-in hotspot passes client-to-client traffic and
   multicast.** If it does, the two-to-five device case needs no software at all.
   If it does not, that is worth knowing before recommending it.
5. **Injection at HT/VHT/HE rates**, which is now the only path by which better
   hardware helps the carousel.
